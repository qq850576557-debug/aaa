## 结论及证据边界

普通新增人员不是必然失败的操作：当前同版本前后端可正常新增施工人员、项目经理、多工种人员，立即编辑、分配、排序、刷新和重新登录后均能读到持久化结果。没有发现当前表单漏填必填字段、随机重复 ID 或必须新增数据库字段的问题。

**可以确认并已修复的是故障扩散机制，不能确认生产现场第一次 400 的具体输入。** 未取得故障服务器前后端 SHA、失败响应及原草稿，所以不能断言那一次就是新增人员生成错误、版本不一致或生产数据损坏。新诊断可以在后续真实故障时区分这些原因。

### 已复现的完整因果链

1. 人员、工种、任务、项目、备忘和聚合采购提醒共用 `App.mutate` → `useCloudWorkspace.update` → `PUT /api/workspace`。没有单独的人员 CRUD/排序接口。
2. 原 hook 对 400/401/403/409/413 统一设置全局 `blocked`。单次人员校验拒绝、真实冲突或工种删除失败均可把其他页面的保存一起锁住。之后 `update()` 在发送请求前就报“请先核对保存冲突或恢复草稿”。
3. 原 API 使用通用 `valid()` 包装，吞掉了校验路径，前端只知道“数据校验失败”，无法定位拒绝的记录。
4. 原启动逻辑把任何恢复出的草稿都设为阻塞，旧失败状态因刷新持续存在。网络失败没有自动续传，也没有请求超时，可能长时间停在保存中。
5. 增加真实并发测试后发现：全局人员操作会给选中项目附带 `updatedAt`；它与另一客户端删除该项目竞争时，整条记录比较把时间戳变化误认为项目业务编辑。使用数据库行锁屏障强制删除先提交，修复前返回 `[409,200]`，修复后 `[200,200]`。真正修改项目备注再与删除竞争仍然报冲突。
6. 关联冲突还有两个边界：本地未保存子记录所属工地被删除时，无关工地的 SSE 更新可能无法显示；本地删除人员、云端新增人员分配时，保守关联冲突可能连无关采购都一起搁置。新增回归先失败，修复后通过。

不是简单关闭全局 CAS：服务端继续在同一事务中锁定工作空间、验证账号绑定的签名基线、合并字段意图、检查业务关系、提交关系表及审计回执。没有改为无条件快照覆盖，也没有重建存储架构。

## 数据结构与关联核查

- `src/lib/model.ts` 的人员字段：稳定 ID、姓名、工作职责、传统工种文本、备注、是否参与分配；人员工种 ID、类别 ID、软删除标记兼容旧记录。空工种和备注合法。新增采用现有 ID 生成器。
- 人员显示顺序保存在人员数组顺序；`$order` 只是合并冲突的标识，不是一个新人员 ID，也不是需要新增的数据库列。
- 人员工种来自 dictionaries；人员工种基础类型与项目 trades/施工阶段仍分开。现有历史阶段引用未删除。
- 项目、工种、任务的 `staffIds` 指向稳定人员 ID。关系表 `person`、`assignment` 与工作空间快照在现有事务内一致保存。事务失败回滚，不只改快照不改关系表。
- 项目经理、设计人员、监理的关联及文本兼容逻辑未改变。甘特图日期、人员履历/内部评价、考核、采购历史及账号关联规则未改。
- 人员软删除保留原 ID 与历史关联。新增人员不会自动创建账号，也不会赋予读取人员手机号等私密资料的权限。
- 不兼容的旧历史恢复从通用 500 改成明确 409；保留关联校验，拒绝恢复时整个状态不变。有效的删除前人员快照可正常恢复，并保留任务和考核关联。

### 草稿和保存保护

- 一次发送前先持久化完整草稿及精确请求。发送结果不明时不生成新请求编号、不改请求体；现有同事务审计回执确保重试幂等。
- 自动重试间隔为 1/2/4/8/16/30 秒，最高 30 秒；联网/页面重新获得焦点也会尝试恢复。401 或签名/会话安全失败仍保护性暂停，需要恢复有效身份，不能绕过认证。
- 服务端明确拒绝的记录及依赖暂缓提交；用户修正资料后重新尝试。没有静默丢弃字段或自动采用云端。
- 真正同字段冲突仍需用户选择。暂缓核对不锁住其他记录。选择前保留完整原草稿恢复副本。
- 旧草稿结构不兼容时，不删字段强行解析；保留原始槽和原样归档，换新草稿槽继续使用当前云端，并提供恢复包。旧内容仍需人工核对后通过现有受控导入/恢复流程处理。
- 原有业务备份下载、数据库备份/恢复机制均未移除或改写。浏览器存储完全不可用时不发送无法记账的请求，继续明确提醒紧急备份，不假装已经安全保存。
