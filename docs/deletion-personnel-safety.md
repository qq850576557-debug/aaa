# 已删除记录与重复人员防护

验证日期：2026-11-03（北京时间）。基线 `821918f4ec99eb97e389ece0b1f7d97de0585360`。分支 `feat/chunmo-project-manager`。

## 调查结论和证据边界

用户确认看到的是多个独立人员卡片，不是下方历史姓名按钮。本轮没有访问生产数据库或审计，不能认定线上这批卡片一定来自旧系统、某次导入或某个账号。

代码中发现并复现两条风险路径：

1. 本地草稿为了保留未提交子记录，会保留已被云端删除项目的旧关联图。过去正常页面直接展示此图，可能把已删除项目和旧排班显示成当前数据。这种页面重现不等于云端已经重新入库。
2. 普通新增没有检查该ID是否曾删除；一个被当成新增的旧ID可绕过单纯“当前集合中不存在”判断。不同ID但人员资料一致的新增也没有防重检查。

截图是同一人员ID在两个不同工地的任务重叠：2026-11-23至2026-12-10，自然日含首尾共18天。若该人员和分配仍有效，提示应保留；不能以隐藏真实重叠作为修复。核实具体线上分配及重复产生者仍需要对应生产审计证据。

## 修复

- 正常页面使用只读投影：已在云端删除的项目和人员不再从旧草稿显示成当前档案，相关旧任务不再参与正常页面冲突计算。真正的新建未同步项目仍可展示。被服务端明确拒绝的旧ID或重复新增也只留在恢复核对中；完整原草稿、关联及恢复副本保留，可在冲突核对与紧急导出中查看，未修改草稿原内容。
- 服务端普通保存和备份导入检查追加审计中的删除ID，拒绝隐式重新创建；人员软删除标记也不能被普通保存取消。新旧全量/增量保存均受保护，原请求回执先行校验，重放不会重新写入。明确的负责人历史恢复路径继续保留。
- 追加审计不受15天界面历史保留期限制。本轮不建立新表、不添加迁移，也不补造历史删除记录：若某旧ID的删除早于可用审计且当前无删除标记，不能凭空断定它是旧删除记录。
- 新增人员时前后端检查规范化姓名、类别、原工种、工种ID集合、备注构成的资料指纹。不同ID且资料一致时拒绝重复创建，包括与已删除档案相同的资料；确属同名不同人员时需补充区分信息。服务端检查在事务内针对最新状态执行，抵御多人同时新建。使用一次分组，避免批量新增产生平方级资料对比。
- 不合并、删除或规范化写回已有同名档案；同名且资料不同的独立ID继续保留。旧记录的正常编辑及其他无关项目/采购保存不受新增校验牵连。
- 冲突面板增加“核对任务分配”入口，打开原任务编辑器。待同步排班明确标注为本地预览，仍按人员ID、有效任务和日期检测，不按同名推断身份，不自动调整任何工期或分配。

## 数据保留

| 原内容                           | 处理                                        |
| -------------------------------- | ------------------------------------------- |
| 用户刚删除的档案、项目           | 维持删除意图，阻止旧草稿隐式恢复            |
| 旧草稿和被删除父项的关联图       | 保留在原日志/恢复核对中，正常页面投影不复活 |
| 现有同名档案                     | 原ID及内容保留，不自动合并或清理            |
| 人员任务、采购、事项、历史及审计 | 沿用原结构、事务、回执、权限与恢复能力      |

没有清库、重建数据、自动分类、真实资料迁移或阿里云部署。生产内容及这次线上重复卡片的直接来源未核查；测试数量不能代表生产档案数量。

## 验证

284项不重复用例通过，0项未通过：单元164、API/PostgreSQL77、云端浏览器28、本地人员及工种浏览器15。前后端构建及格式检查通过。

- API：删除后before-null增量重建、普通全量重建、取消人员软删除均被拒绝；失败无写入。新ID的真实新项目和同名不同资料人员仍能创建，其他字段保留。原可信历史恢复及审计回归通过。
- 浏览器：断网编辑后另一个会话删除项目，刷新恢复不会在正常项目栏重现已删除项目，完整待核对内容可导出。重复资料建档被拦截，原档案不变。
- 多人：10账号并发、无关项目独立保存、SSE更新、刷新、断网续传及原回执保护通过。
- 排班：同名不同ID不混用，已删除ID不会借用同名在用ID参与检测，真实重叠仍显示，解除分配后消失。
- 最后两个旧浏览器断言已按新行为更新并复测：剩余项目自动成为当前项目时使用“编辑当前项目”；同名不同人测试补充独立资料，保留原身份/分配断言。77项完整API之后对最终线性资料分组再做2项定向复测通过。

部署后客户端需加载新前端；不应通过清除浏览器IndexedDB来“修复”，这会损坏尚未上传内容。前后端应一起更新，单独更新前端不能替代服务端保护。
