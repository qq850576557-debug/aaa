## 数据、接口与兼容性

迁移文件：`server/migrations/011_record_owner.sql`，仅增加：

```sql
ALTER TABLE work_record ADD COLUMN owner text NOT NULL DEFAULT '' CHECK (char_length(owner) <= 100);
```

API 的 owner 为可选字段。旧客户端更新时省略它会保留原负责人，不能把新资料清空；schema 不给旧请求强行加默认字段，保持原幂等请求摘要形状。已有事项的标题、内容、跟进、状态、日期、版本及创建/修改时间不变。迁移可重复验证，未改任何已应用迁移的校验和。

仅在 `localhost/chunmo_test` 及带 `_test` 后缀的临时数据库执行了迁移测试；生产尚未执行。以后发布此版本须同时更新前后端并按现有迁移流程应用 011，本轮没有执行这些发布操作。

采购继续走现有工作空间事务、签名基线和幂等回执；事项继续走独立记录事务、记录版本与请求编号。两种新建不会同时写两套业务记录，无需新增跨表双写。创建人、修改人、时间和历史仍由服务器生成，负责人只是普通业务字段，不能用来伪造操作人或权限。

工作空间的 CAS、草稿恢复、超时精确重放、独立记录失败隔离均未取消。事项完成操作防重复点击，并沿用稳定请求编号；失败保留当前记录并明确提示。SSE 更新通知复用原有记录通知，不通过本地旧快照覆盖服务器数据。

历史日常事项仍使用原 Note ID 和原编辑/完成逻辑，不自动转换为看板事项；它们可按日期继续显示。旧项目备忘保留在数据库/业务备份和历史中，首页不再放置备忘卡片。复制项目、导入备份仍保留原内容；七阶段模板仅用于新建空项目，不把旧项目强制改成七阶段。

本地演示模式延续原来的限制：事项看板需要登录云端，分类器会说明并禁用该选项；没有制作虚假的本地审计。采购及旧本地记录继续沿用现有本地存储能力。

## 人工验收

1. 打开工地：只见今日与明日两卡；采购和事项有类型、项目、日期、状态，空状态和多条内容布局稳定。
2. 分别点两个新增入口：未选类别无法保存；选采购和事项展示不同表单，更换类别会提示确认。
3. 保存采购后进入采购清单；保存事项后进入项目看板。修改日期后回首页检查归属，完成和删除不会影响另一类记录。
4. 新建两个空项目：均为七阶段、零任务、颜色顺序一致。修改其中一个阶段颜色、名称、顺序后刷新，另一个与旧项目不变。
5. 人员管理勾选工种：只看下方勾选，不出现上方重复名称；搜索、取消勾选、清除和工种管理仍可用。旧阶段引用保留。
6. 手机重点检查分类表单、内部滚动、底部导航、阶段编辑、跨行/上下排序操作及真实使用中的长标题。

负责人已授权在全部必要检查通过后提交并正常推送开发分支；实际提交号及远程一致性以 Git 核对结果为准。本轮没有部署或执行生产迁移。
