# 团队成长模块产品建议（规划，尚未实现）

先保证施工质量、真实业务数据和权限可靠，再引入轻量认可。当前软件没有员工账号、成员列表、团队排名、徽章发放或云端同步；本阶段只提交本方案，不增加相关界面和数据库实体。

## 产品边界

围绕可核验工作成果：高质量交付、问题闭环、阶段复盘、经验共享与协作支持。禁止以施工速度作为唯一评分标准，不奖励跳过质量检查，不设羞辱排名和强制每日打卡。不用项目进度百分比推测个人绩效。

## 建议能力

1. **项目里程碑徽章**：首个完整交付、完成阶段复盘、采购计划管理规范、施工问题闭环、质量验收通过。徽章需附项目、证据、确认人和时间，允许撤销误发；对质量问题保持申诉与纠正入口。
2. **个人成长档案**：参与项目和工作阶段、专业技能学习、处理过的问题、复盘记录及经验分享。区分本人草稿、团队可见和管理员可见，离职后按组织政策处理，不公开敏感业主资料。
3. **协作感谢**：感谢必须对应具体项目或协作成果；不与薪酬自动绑定，不进行人气排名，限制刷赞。被认可者可选择是否公开展示。

## 分阶段实施顺序

- 阶段 A：在核心工期稳定后，先建立账号、组织、成员身份与服务端权限检查。明确组织与项目隔离、数据所有权、审计记录、隐私及导出删除规则。
- 阶段 B：建立有证据的验收/复盘/问题闭环记录；设计经理复核和纠错流程，不做员工分数。
- 阶段 C：小范围试用里程碑徽章和个人档案。人工确认发放，成员有知情、隐藏和申诉能力；衡量经验复用与质量稳定性。
- 阶段 D：验证需求后增加协作感谢，再单独评估同步和跨设备访问。没有后端权限校验前，不在本地数组中虚构团队功能。

## 数据与技术边界

当前所有实体以项目 ID 隔离，持久化位于 `storage.ts`。未来由 API 端提供 tenant/project/member 身份验证、权限决策、版本号、审计和同步冲突处理。本地记录迁入云端必须先备份、预览映射、验证数量和关联，再由用户确认；禁止把浏览器 IndexedDB 误称为服务器保存。员工成长资料应与施工交易数据分开授权，感谢和徽章不应阻塞施工主流程。

## 待核心稳定后的用户决策

先访谈成员和负责人，确认谁能看哪些成长记录、谁能核验成果、是否自愿展示、保留多久及如何纠错。完成这些产品与权限决定后，再估算开发和部署成本；当前不部署、不产生服务器费用。
