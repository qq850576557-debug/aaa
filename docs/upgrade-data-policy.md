# 重大升级与真实业务数据保护

此规则来自创始人2026-11-01的明确要求，并在根目录AGENTS.md长期生效。

默认方案A：保留旧数据，只隐藏或停用界面。UI取消不构成删除、覆盖、重分类、字段清理、草稿清空或生产迁移授权。方案B为建议迁移，必须先列出真实来源、稳定ID、项目、数量、日期、负责人、状态、历史、未识别记录以及目标映射，再由创始人审批。方案C删除只限明确批准的具体范围，并先完成可恢复备份。沉默不是同意。

流程：升级前只读检查 → 识别旧数据 → 提供保留/迁移方案 → 创始人审批 → 备份并验证恢复 → 独立测试环境验证迁移 → 获准正式执行 → 核对数量和重要字段 → 验收。

## 只读检查工具

旧部署尚未具备新API时，先由管理员在确认的数据库执行以下只读SQL，无需先迁移或启动新版服务：

```bash
sudo -u postgres /usr/pgsql-17/bin/psql -X -d chunmo_staging -f /opt/chunmo-source/deploy/native/upgrade-inventory.sql
```

此脚本在数据库强制只读、可重复读事务内查询，逐工作室及项目列出计数和来源，只查询旧库已经存在的表。不存在的新表不自动创建；未知列表类型的数量为空值，不能当成零条。输出按工作室隔离，应私下保存供创始人审批，不含密码或私密密钥。脚本不执行数据库迁移、不删除记录，也不启用新版API。

升级后的负责人可从「事项管理 → 历史数据分类与兼容」下载「升级前数据清单（只读）」。接口`GET /api/upgrade-data-preview`只查询当前工作室原始计数与项目分布、历史节点及保留表数量，不改数据、不迁移、不清理；普通成员403。旧结构无法识别时列出来源与索引，数量未确认用空值标记，未知根字段保留待核查，不把异常结构当成零条记录。

复用`GET /api/legacy-migration/preview`逐条查看旧来源、原文、稳定来源标识、推断原因、已有目标匹配、待确认及资料分类。候选分类不是迁移授权，不能启动时自动提交。原有迁移程序保留签名预览、备份确认、版本检查、幂等来源链接和事务回滚。

## 本轮数据库兼容方案

014_mentions.sql只追加事项多人关联字段和通知表/索引，不删除、更名或重分类旧字段，不把原负责人姓名转换成猜测的账号ID。原事项默认mention_ids为空，原采购mentionIds可缺省。旧客户端省略新字段时保留已保存关系，显式空数组才表示取消。旧历史快照缺新字段时，事项恢复保留当前关联。历史恢复/导入不回放@通知。

014及配套最小授权仅应用于独立localhost测试库。通知表只允许应用追加、读取及更新read_at，不能修改消息原文或删除历史。生产部署和结构迁移仍待创始人审批；生产历史业务重分类迁移是另一项审批，本轮不执行。

## 真实数据核查边界

本轮没有阿里云数据库或各员工浏览器的直接访问权限，生产真实项目/记录/未同步草稿数量均未核查。不得把测试工地数量当成实际经营数据数量。部署前须下载上述只读清单、旧源预览及完整可恢复备份，填写逐项目核对表后再审批。任何无法识别或无法映射的旧记录保持原样，列入待确认。
