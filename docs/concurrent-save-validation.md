## 根因证据

原 `src/lib/useCloudWorkspace.ts` 将整个工作室 Data 以 `{revision,data}` 提交，`revision.current` 在请求执行时才读取。`server/store.ts` 的 `commit()` 锁定唯一的 `workspace_state` 行，只要其全局 revision 不等于客户端版本就返回 409。一个工地的采购修改会递增所有工地共用的版本，因此另一个工地的施工修改也被拒绝。

SSE 每秒检查版本；编辑弹窗、拖动或本地保存期间，客户端有意延迟读取，以免替换正在编辑的内容。因此 SSE 不会为旧页面补上安全合并能力。原有队列也没有可靠的基线来区分排队的新编辑和快照中已过时的字段。

原草稿仅在内存。原“重新读取云端”会整份替换当前数据；`beforeunload` 只提供离开提示，没有持久草稿。

新增 API 测试保留旧协议并用真实同时发出的请求复现：同版本修改不同工地，结果仍为一个 200、一个 409。这既证明根因，也验证旧协议没有被悄悄改成无条件覆盖。

## 最小修复机制

### 原事务和 CAS 保留

`server/store.ts` 的写入、图关系重建、权限、采购期限审批、完成/恢复权限、业务审计和历史记录不变。独立的材料、考核、记录看板资源继续使用原来的版本和幂等机制。

GET `/api/workspace` 及保存响应新增 `baseProof`。新客户端保存仍调用同一 PUT API，同时携带原始 `base`、`revision`、`baseProof` 和 UUID `requestId`。缺少新字段的旧客户端仍走原有严格 CAS；新字段必须完整提供。

`server/workspace-save.ts` 使用现有服务端密钥、独立 HMAC 域，对工作室 ID、当前账号 ID、版本和原始数据生成签名。服务端验证该签名，禁止客户端编造“原始值”来绕过合并判断。会话、CSRF、当前角色和业务校验仍单独执行，签名不是登录凭据。

在同一数据库事务内锁定工作室最新状态，按 ID 和字段比较可信原始值、本地修改值、云端最新值：

- 未修改字段采用最新云端内容。
- 不同项目、记录和不同字段的修改可合并。
- 同字段改成相同值不构成冲突；改成不同值返回真实字段及三方内容。
- 删除/编辑、同 ID 的不同新增、不同的项目排序需要明确选择。
- 日期或跨记录关系组合后失效时，升级为明确的整条记录选择；仍无效则拒绝保存。不会自动删除子记录或恢复已删除的项目。
- 项目 `updatedAt` 是原有 UI 元数据，不将其误判成业务字段冲突；可信操作时间仍由原审计生成。

合并后再次执行完整模型验证，并调用原 `commit()`，其 CAS 使用已锁定的最新版本。没有关闭 CAS，也没有把客户端传来的新版本号直接用于覆盖。

### 幂等与连续编辑

提交回执复用现有追加式 `audit_event`：`workspace.submit` / `workspace_submission`，只记录请求摘要，不记录密码、密钥、签名或完整请求体。回执检查和写入与业务写入共享事务及工作室行锁。相同账号相同提交内容重复请求返回最新状态，不重复创建、完成、写历史或递增版本；相同编号不同内容拒绝执行。

前端一次只保留一个在途提交。网络错误或 5xx 结果不明确时，保留并重试完全相同的请求。确认成功后，将请求发出后产生的新编辑相对于已提交视图重新合并，不会只升级版本号再发送旧快照。

工期“撤销”也只逆转本次调整；其他人的独立修改保留，同字段又被修改则拒绝直接撤销。

### 草稿与重新读取

复用已有 `idb` 依赖，新增独立浏览器数据库 `chunmo-cloud-drafts` v1，保存账号、工作室、标签页、草稿、合并基线及准确的在途请求。它不打开或写入原 `chunmo-workspace` 业务数据库，不是 PostgreSQL 迁移。

每次编辑按顺序写入草稿；发请求前必须成功落盘。存储受限或容量不足会明确报错，阻止该次网络写入，保留内存草稿与离开保护，并提供紧急备份。草稿基线无需存历史，因此不重复保存整份历史档案。

同一标签页刷新并通过原账号身份校验后恢复草稿，不自动提交；其他账号或工作室不自动载入该草稿。支持 Web Locks 的浏览器会为复制出的活动标签页分配独立草稿槽，避免相互覆盖。

“重新读取云端”现在核对并合并，保留本地意图。存在不确定的在途提交时先要求重试回执；有打开的表单或读取期间发生新编辑时拒绝替换。真正的冲突显示原值、本地值、最新云端值，只有明确选择后才保存，提交前仍再做服务端合并及校验。

## 限制与后续验收

- 历史恢复、整体导入和负责人采购延期审批仍采用原严格全局 CAS，不会自动重放这些高影响操作。它们的冲突需重新核对后明确操作。
- 底层仍是工作室快照和串行事务，没有改成新的存储架构。不同记录可合并，但不是无锁并行写库；本轮没有对大体量数据或真实广域网进行长时间压力测试。
- 现有 16 MB 请求限制继续保留；请求现在同时包含原始与修改快照。超限会明确失败并保留草稿，不自动提高生产限制。
- 浏览器草稿不是服务器备份。清除站点数据、无痕窗口结束、存储损坏或设备故障可能失去本机副本；应保留现有导出和服务端备份。恢复主要针对原标签页刷新/会话恢复，不声称已经提供跨设备草稿同步。
- 未验证缺少 Web Locks 的老旧浏览器中的复制标签页隔离；常规独立标签页 ID 仍存在。
- 前后端应以同一版本交付。旧页面仍使用严格 CAS；新界面面对旧服务端会明确拒绝不安全保存。生产尚未升级，不能声称已消除线上问题。

负责人可在验收环境用四个账号分别打开不同工地编辑并保存，再用两个账号同时修改同条采购的不同字段、同一字段；确认前者保留双方修改、后者展示三方内容。发生冲突后刷新页面、重新读取云端、选择冲突字段并保存，验证其余草稿不丢失。上线安排仍需单独验收。
