# 事项读取失败与SSE误退出修复

2026-11-01，`feat/chunmo-project-manager`。未连接阿里云，未操作生产数据库。

## 证据与边界

用户Network截图：`session/workspace/presence`为200，`records`为400，`events`为200但约1.08秒结束。仅凭截图不能确定服务器具体缺失的迁移或授权，仍需服务器迁移清单及日志核对。

代码确认的缺陷链：

1. 原生部署迁移白名单只到010，实际SQL目录已包含011—013，完整部署会安全拒绝新迁移；原API启动却只检查010，手动混搭发布可能启动结构尚未就绪的新API。
2. 新版`GET /api/records`读取011新增的`owner`及012新增的`legacy_record_link`。缺字段、缺表或运行授权不足分别产生42703、42P01、42501，但旧通用错误处理将其错误返回400“数据校验失败”。
3. SSE每秒查询事项历史及012关联表。查询任何异常时旧代码都发`session-expired`，前端正常执行安全锁定，因而显示登录页。这不是会话真正失效的可靠证据。

隔离测试实际重现了010旧库缺owner/关联表；故障注入重现了数据库错误触发SSE结束的路径。生产的具体SQLSTATE尚待核实，不把推测写成已查证的生产数据事实。

## 修改

- 明确审查并登记011、012、013原文件哈希，新增部署清单回归测试；没有修改任何已存在SQL，没有关闭校验。
- API启动前只读检查010—013和关键表读取/新增历史快照所需授权；拒绝半升级启动，不自动执行DDL或授权。
- 完整部署在配套授权后使用真实应用连接执行同一就绪检查，失败则在切换发行版本之前停止。
- 缺表/缺字段/权限及已识别连接故障返回明确503，记录脱敏SQLSTATE；不暴露SQL、业务正文或连接串。
- SSE区分真正会话撤销与数据库/网络故障。前者仍通知登录失效，后者只结束连接交由原生EventSource重连；客户端断开也不再伪造失效事件。
- 保留所有CAS、事务、草稿、回执、权限和业务数据结构。无新增数据库迁移。

## 现场处理

先执行部署文档中的只读命令，核对源码SHA、实际发行SHA、数据库迁移清单与日志。仅拉取源码不等于部署成功。

经负责人确认、完成可恢复备份后，使用已有完整部署流程应用011—013及配套授权，再启用匹配代码。不要清库、删除迁移台账、清草稿、关闭校验或赋予应用超级用户权限。012只建兼容结构，历史业务分类迁移仍须单独预览确认。
