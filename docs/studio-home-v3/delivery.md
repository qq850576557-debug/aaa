## 功能及权限

每日必做只编辑工作要求和关联员工。未指定员工即全体员工；新要求每天有效，不生成项目事项或打卡记录。多选、搜索（人员超过六人时显示搜索框）、编辑和确认删除均可用。每日列表继续支持展开/收起。

卫生值日按选择顺序循环，每 3/7 天一人。当前人员仍在新顺序中时保留当前人员，否则从新名单第一人开始；界面明确预览保存后的结果。起始日期修改会带入当前计划日期，也可单独调整当前轮次。记录实际完成后，下一人计划日期为实际完成日期加当前间隔。配置变更保留已完成历史；最近一次完成日期可以修正，追加 corrections 而不改写原 history。较早历史只读，本轮不做任意历史重写。

查看排班为居中系统 dialog，支持 Escape、关闭按钮、焦点恢复、上/下周和内部滚动。按 Asia/Shanghai 的服务端当天决定本周；日历运算使用日期加天数，覆盖跨周、跨月。显示本周实际完成/计划记录、当前轮次及近期下一轮，未来日期明确标为计划。

所有管理能力仅由 `cloud_workspace.owner_account_id` 对应的现有真实所有者账号获得。`server/auth.ts` 从该关联计算 actor.owner；**不以 account.role、用户名、普通管理授权或前端参数判定**。前端仅在服务端 owner 为 true 时挂载管理入口和表单；PUT 和新增 POST 都使用原 owner 中间件。员工只能收到当天有效且分配给自己/全体的工作要求，以及本工作室只读值日排班。

原 Cookie、CSRF、Origin、事务、审计、version CAS 和 requestId 精确幂等回执保留。新旧操作的回执摘要分开，原 PUT 摘要兼容。未知保存结果保留原请求编号重试；409 保留输入、读取最新配置并要求核对后再保存；关闭弹窗再打开保留本页内存草稿，刷新前有未保存提示。没有承诺浏览器强制关闭后恢复未提交表单。

## 数据映射与兼容

| 原数据                     | 本轮处理                                                     |
| -------------------------- | ------------------------------------------------------------ |
| rules 的 id/text/people    | 继续使用同一记录；只编辑当前选中要求                         |
| enabled/weekdays/from/to   | 保留原值并继续用于旧规则有效性判断，仅隐藏控件               |
| weekly/exceptions/cleaning | 完整保留；尚未设置新轮换时仍可查看原周排班                   |
| 原提交回执及审计           | 保留，不清理、不改写                                         |
| 新轮换配置与完成历史       | 在同一个 studio_daily.value JSON 中增加可选 rotation，无新表 |

**没有新增 SQL 迁移、数据库或付费服务。** 依赖已在前一轮批准的 015 表结构，015 文件及审批清单本轮未修改。旧周排班不会自动迁移成新轮换；旧规则的停用、星期和有效期不会被悄悄改成每天有效。没有执行真实记录的批量清空、删除或重分类。若希望解除旧规则日期限制，应另列真实记录范围取得创始人批准。

新增接口 `POST /api/studio-daily/rotation` 仅接收 configure / complete / correctLast 命令。历史由服务端构造，不接受客户端整份覆盖。普通 PUT 不得修改 rotation；旧客户端遗漏 rotation 时服务端保留现值，防止旧设置保存清空新历史。新分配的人员必须为同一工作室有效账号；旧规则未改动的历史人员关联不强制清除。

生产旧数据数量、具体旧规则、015 是否已实际运行，以及服务器当前版本，本轮均**未远程核查**。测试账号数量不能作为生产盘点结果。

## 上线前检查与回退

本轮没有连接阿里云执行部署、没有执行 chunmo-update、没有操作生产数据库。

1. 安排上线前确认生产真实所有者账号，以及 015 已安装或按既有明确批准执行；保留数据库/配置/发行目录备份并验证可恢复。
2. 先核对当前 release 和 API、web、两个独立小程序服务。以下读取不输出配置密钥：

   ```bash
   readlink -f /opt/chunmo-staging/current
   systemctl is-active chunmo-staging-api chunmo-staging-web chunmo-mini-photo chunmo-mini-workbench
   bash /opt/chunmo-staging/current/deploy/native/health.sh
   ```

3. 经创始人安排上线时，沿用仓库现有托管发布器，以本轮最终报告的完整 SHA 固定前端/API 一起发布。不要只替换前端，否则轮换接口不存在。最终报告附可复制命令；本轮不执行该命令。发布器会创建原有备份、检查已批准迁移、构建/审计并在失败时沿用代码回退流程。
4. 发布成功后再次执行上述健康检查；实际最高负责人编辑一条经授权的真实要求，员工确认可见范围。确认 3/7 天预览、当前轮次与实际日期，再决定是否正式启用新轮换。不要为了验收往生产植入示例员工或制度。
5. 若代码回退，保留 JSON、新轮换历史和所有回执，不执行向下迁移或用旧备份覆盖现有数据。回退到旧 API 后暂停工作室日常编辑，恢复新版历史保护接口后再继续；不得通过旧接口手工提交遗漏 rotation 的设置。

本轮没有新的生产迁移待审批，也不需要重分类旧有效记录。实际生产备份、发布和负责人/员工验收尚未执行。
